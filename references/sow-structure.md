# SOW structure and how to write each section

The order and level of detail follow a reference Jelou SOW (two agents, WebViews, API integrations) that the team considers the model to reuse. The SOW is written in Spanish; section names are given in English with the Spanish heading in parentheses. Every section below is generated by `scripts/build_sow_docx.js` from the matching part of `sow.json`.

| # | Section | What it must contain | Typical error it prevents |
|---|---|---|---|
| – | Cover (Statement of Work) | Client, provider, version and status, date, prepared by, priority | Documents with no version or owner |
| 1 | Project name (Nombre del proyecto) | One sentence naming the agents and the client | Ambiguous titles |
| 2 | Brief (Brief del proyecto) | Need, solution and why it matters, plus the design principles | A generic brief that does not mention the business |
| 3 | Objectives (Objetivos) | General, specific, and per agent; measurable | "Improve the experience" with no metric |
| 4 | Team (Equipo de trabajo) | Name, organization, position and responsibility per role; roles AM/PM/support; weekly follow-up | Missing client technical owner; invented names |
| 5 | Scope (Alcance) | Phases and requirements (R1, R2) with audience and channel; admin features; user features per agent; **out of scope** | Promises the bot later does not keep |
| 6 | Operating parameters | Hours, holidays, language and tone, currency, taxes, retries, retention, phone identification, test data | Decisions discovered while building |
| 7 | Conversation map and E2E diagram | General orchestration diagram; per agent: persona, diagram, stage table with the proposed texts | A diagram that is not what the bot does |
| 8 | User stories (Historias de usuario) | Per agent, ID `HU-<agent>-NN`, As/want/so that, acceptance criteria | Rules nobody can test |
| 9 | Business rules | One per bullet with ID, values and what happens when not met | Rules with adjectives, not verifiable |
| 10 | Technical solution | Which Jelou component delivers each capability; deterministic vs conversational | Promising what the platform does not do |
| 11 | Escalation to a human | Trigger, mode (automatic/offered), destination, hours, out-of-hours message | "Escalate if needed" |
| 12 | Data | Entities stored, fields and retention | Personal data with no policy |
| 13 | Integrations | One card per system: purpose, endpoints, use, connection, authentication, current state, documentation, test environment, condition, owner | Integration with no documented API or test environment |
| 14 | Data map | Per agent: field, applies to, description, required | Fields invented during the build |
| 15 | Validations | Field or rule, validation, proposed message, applies to | Inconsistent error messages |
| 16 | Acceptance criteria and tests | Test list and the UAT rule | Tests that contradict the scope |
| 17 | Effort summary (with AI) | Deliverables by type with hour ranges, management overhead, total | Estimates with no basis |
| 18 | Deliverables and schedule | Milestones with business days and computed dates (project ≤ 20 business days); client dependencies | Hand-typed dates that do not add up |
| 19 | Responsibilities | Two columns: Jelou and the client | Work nobody owns |
| 20 | Assumptions and pending items | Assumptions; pending items with owner | Hidden assumptions |
| 21 | Security review | Aspect, reviewed, mitigation; project risks | A generic copied matrix |
| 22 | Version control | Change log (CC-xx) when the SOW evolves; versions table | Changes with no traceability |
| – | Signatures | Names, positions, date lines | Unsigned scope |

## Guidance by section

**Team.** Ask first whether the user has the data. Roles with missing data stay as `POR COMPLETAR` (red). Never invent names or positions.

**Scope.** Write included features from two points of view: what the end user does on WhatsApp (grouped per agent) and what the client's team does (monitoring, handoff, reports). Write *out of scope* just as seriously: everything someone might assume and will not be done. Each item carries `terminos` so the linter detects it if it reappears in any step, message or story.

**Conversation map.** Long flows (more than 18 steps) are drawn as an overview, one detail per stage and a common handoff figure (F1.1, F1.2…): set `grupo` on the first step of each business stage. Forms are `formulario` steps (`herramienta`: flows | webview | por_definir). Build the graph first (`agentes[].pasos`), then the texts. Each step has: the diagram text (≤ 110 characters), the exact proposed message, the buttons or list rows, the form fields of a WebView, the integration it calls and the rules it applies. A decision always has labeled exits. End every branch in a `fin` step. The stage table in the Word file is generated from the steps that carry an `etapa`.

**Stories.** One story per capability, with Given/When/Then criteria that quote figures, states or exact messages. Every business rule appears in at least one story.

**Integrations.** Describe each system as a card. Say what is read and written, who builds and hosts any intermediate layer, how it authenticates (never the credentials), whether documentation and a test environment exist, who answers on the client side and the current state ("integrated", "to connect", "mock"). If a system is still a mock, say how and when it is replaced.

**Effort and schedule.** Use the AI-assisted rate table (`references/effort-model.md`). The whole project fits in 20 business days; waits on the client are dependencies with dates. Typical milestones: planning and definitions, build, internal tests, client UAT, production, closing.

**Security review.** Aspects of the template (confidentiality, integrity, availability, regulation, staffing, delays) with a mitigation specific to this project, plus risks of the project.

**Versions.** 1.0 is the initial version; corrections during review are 1.1, 1.2; a new baseline is 2.0, 3.0 (up to 3 version controls). Approval is `meta.estado` (`en_revision` | `aprobado`), never the number; there are no 0.x versions. For a SOW that evolves, add one change per row (`cambios`: ID, date, area, description, evidence, impact) and a note about commercial impact when scope changed after the offer.
