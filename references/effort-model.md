# Effort model with AI (Claude automates almost everything)

Machine-readable rates: `scripts/lib/effort-rates.json` (this file explains them). The SOW carries them in `esfuerzo` (format in `references/sow-json-format.md`, section "Effort with AI"); each `items[].tipo` must be a key below.

## What these numbers are

**They are ESTIMATES for AI-assisted work, not measured data.** Assumption: Claude Code with the Jelou CLI and skills produces almost all of the draft (workflows, tools, functions, templates, front, test cases, documents); an experienced human reviews, tests on real WhatsApp and decides; the client answers in reasonable time. Hours are Jelou team work hours, not calendar time. Rates exclude external waits (Meta, client, gateways) and the client's own UAT time (Jelou's support during the UAT is the item `uat_acompanamiento`).

**Calibration:** after 3-5 real projects, replace these ranges with logged hours. Until then, tell the reader in the SOW that effort is an estimate.

## The two caps

1. **Hours cap: 72 h per project, management INCLUDED** (default `meta.tope_horas: 72`, configurable). The linter ERRORS when the **maximum** total (items x quantity, plus management) is above the cap, unless `meta.excepcion_horas` explains why (then it is a warning). *Default pending business confirmation: whether project management counts inside the 72 h.* If business says it does not, set `meta.tope_horas` to the agreed figure or change the check in `lint_sow.js` (section 14) and this file.
2. **Calendar cap: 20 business days end to end** (rule below, unchanged).

A typical project lands well below 72 h with these rates. If it does not, the scope is too large for one SOW: split it into phases (preferred), or justify the exception. Never hide an overrun by lowering hours.

| `kyc` | 1.5-3 | Marketplace tool and `kyc onboard` exist; tune rules with real documents and compliance review. |
| `pagos` | 1.5-3 | Marketplace tool exists; wire statuses, provider certification, real-credential tests. |
| `integracion_api` | 2-4 | Per endpoint or endpoint group; Claude reads the docs and generates the client; human time goes to authentication and tests against the client's environment. |
| `datum` | 1-2 | Base plus 3-5 collections: schema and CLI creation; large imports add cleaning. |
| `base_conocimiento` | 1-3 | Per document set: cleaning/chunking by Claude, human curation. |
| `campana` | 1-2 | Config, CSV and test; real send needs human approval. |
| `handoff_asesor` | 1-2 | CONNECT node is simple; teams, hours and rules are set in the dashboard. |
| `agente_faq` | 2-4 | FAQ AI Agent (prompt, guardrails, fallback, test cases); knowledge base counted separately. |
| `canal_whatsapp_activacion` | 0.5-1.5 | Short work; Meta verification and Business Manager access dominate the calendar (dated dependencies). |
| `capacitacion` | 1-2 | One operator/admin session plus guide and map generated by Claude (jelou-graph). |
| `pruebas_qa` | 2-4 | **Internal tests**, per agent: `jelou-test-workflows` runs draft cases, human reviews and does a real-WhatsApp pass. Milestone "Pruebas internas". |
| `uat_acompanamiento` | 1-3 | **Support during the client UAT**: prepare cases and test data, attend observations, fix what is in scope. Milestone "UAT del cliente". |

`gestion_pct`: 10-20 % over the item total (coordination, status, client communication); **15 by default**, included in the 72 h.

Every SOW must carry both test items: `pruebas_qa` (internal) and `uat_acompanamiento` (the linter warns when either is missing), matching the two explicit milestones of the schedule.

## Ratio table (hours per type, with management at 15 %)

Use it to sanity-check a scope before filling the items. Maximum hours per unit with management: `workflow_simple` 1.7, `workflow_medio` 4.6, `workflow_complejo` 11.5, `function` 3.5, `webview_simple` 3.5, `webview_backend` 6.9, `flow_whatsapp` 3.5, `integracion_api` 4.6, `datum` 2.3, `campana` 2.3, `plantilla_hsm` 0.6, `pruebas_qa` 4.6, `uat_acompanamiento` 3.5.

| What fits in 72 h (maximum, management included) | Total |
|---|---|
| 1 complex agent + 2 medium workflows + 1 function + 1 backend webview + 1 Flow + internal tests + UAT support | about 43 h |
| 3 medium workflows + 2 backend webviews + 2 API integrations + 1 function + campaigns + tests | about 55 h |
| FAQ agent + knowledge base + handoff + channel + training + tests | about 24 h |

Rule of thumb: one complex agent costs about one sixth of the cap.

## How to choose within the range

- Go to the high end (or above) when: no client test environment, undocumented API, several channels or languages, regulated sector (banking, insurance, health).
- Go to the low end when a similar project exists that Claude can reuse as a reference.
- `cantidad` multiplies the range; put the reason in `nota`.
- Per-project totals: `horas_min` = sum(min x cantidad); `horas_max` = sum(max x cantidad); both multiplied by (1 + gestión).

## Calendar rules (set by the user, apply as written)

1. **A project cannot last more than 20 business days end to end.** The linter errors above 20 unless `meta.excepcion_plazo` justifies it (then it is a warning).
2. **Dates are dominated by client dependencies** (accesses, final texts, UAT, Meta approvals) more than by build hours. Those waits must appear in `dependencias_cliente` with a date; do not inflate hours to cover them.
3. **Internal tests and client tests are explicit milestones** of the schedule (`hito.tipo: "pruebas_internas"` / `"uat"`, or the names "Pruebas internas" / "UAT del cliente"), each with business days and computed dates in the Word schedule, the Gantt and the proposal. The linter ERRORS when either is missing.
4. **Formula:**

```
días_construcción = ceil( horas_max_total × (1 + gestión_pct/100) / (personas × horas_dia) )
```

`horas_max_total` is the sum of maxima of all `esfuerzo.items`. `horas_dia` = productive hours per person per day (6 by default). With the 72 h cap one person needs at most 12 days.

5. **Indicative split of the 20 days** (adjust to the case):

| Block | Days (guide) |
|---|---|
| Planning and SOW | 2 |
| Construction | 7 |
| Internal tests (milestone) | 2 |
| Client UAT (milestone, dated) | 4 |
| Production | 2 |
| Closure | 1 |

## UAT time rule (draft clause, pending Legal review)

> Las pruebas del cliente (UAT) deben ejecutarse dentro de las fechas estipuladas en el cronograma. Si vencida la fecha de cierre de UAT el cliente no ha reportado observaciones por escrito, se entiende que el entregable fue probado y aceptado a conformidad y el proyecto se considera cerrado; las solicitudes posteriores se gestionan como control de cambios.

It is printed automatically (with the real closing date) in the schedule section, the client responsibilities and the acceptance/tests section of the Word, and in the pre-kickoff next-steps slide; the SOW also carries a `dependencias_cliente` entry `tipo: "uat"` whose `fecha_limite` equals the end of the UAT milestone. The wording is a **draft pending Legal review**: the linter warns (`LEGAL`) until `meta.clausula_uat_revisada_legal: true`, and the internal faltantes document says so.

## Example 1: one simple agent (FAQ with handoff)

`esfuerzo`: personas 1, horas_dia 6, gestion_pct 15.

| Item (`tipo` x cantidad) | Min | Max |
|---|---|---|
| Welcome and menu (`workflow_simple` x1) | 0.5 | 1.5 |
| FAQ agent (`agente_faq` x1) | 2 | 4 |
| Source documents (`base_conocimiento` x1) | 1 | 3 |
| Handoff (`handoff_asesor` x1) | 1 | 2 |
| Number activation (`canal_whatsapp_activacion` x1) | 0.5 | 1.5 |
| Internal tests (`pruebas_qa` x1) | 2 | 4 |
| UAT support (`uat_acompanamiento` x1) | 1 | 3 |
| Training (`capacitacion` x1) | 1 | 2 |
| **Subtotal** | **9** | **21** |
| **With management 15 %** | **10.4** | **24.2** |

24.2 h <= 72 h. Construction days: 24.2 / 6 = 4.03 -> **5**. Calendar: planning 2 + construction 5 + internal tests 2 + UAT 4 + production 2 + closure 1 = **16 business days**.

## Example 2: two agents with WebViews and an API integration

`esfuerzo`: personas 1, horas_dia 6, gestion_pct 15.

| Item (`tipo` x cantidad) | Min | Max |
|---|---|---|
| Two agents' workflows (`workflow_medio` x2) | 4 | 8 |
| Backend WebViews (`webview_backend` x2) | 6 | 12 |
| Client API (`integracion_api` x1) | 2 | 4 |
| Datum (`datum` x1) | 1 | 2 |
| Reminder templates (`plantilla_hsm` x3) | 0.75 | 1.5 |
| Handoff (`handoff_asesor` x1) | 1 | 2 |
| Number activation (`canal_whatsapp_activacion` x1) | 0.5 | 1.5 |
| Internal tests (`pruebas_qa` x2) | 4 | 8 |
| UAT support (`uat_acompanamiento` x1) | 1 | 3 |
| Training (`capacitacion` x1) | 1 | 2 |
| **Subtotal** | **21.25** | **44** |
| **With management 15 %** | **24.4** | **50.6** |

50.6 h <= 72 h. Construction days: 50.6 / 6 = 8.4 -> **9** (one person) or 5 with two people. Calendar: 2 + 9 + 2 + 4 + 2 + 1 = **20 business days**: fits with zero slack, so every access, text or Meta approval needs a dated dependency and the SOW says a client delay moves the end date.

## Example 3: does NOT fit

Scope: 3 complex agents, 3 `webview_backend`, `kyc`, `pagos`, 3 `integracion_api`, 2 `flow_whatsapp`, `datum`, 6 `plantilla_hsm`, `handoff_asesor`, `canal_whatsapp_activacion`, `base_conocimiento`, 3 `pruebas_qa`, `uat_acompanamiento`, `capacitacion`.
Subtotal 48-100.5 h; with management 55.2-115.6 h. **115.6 h > 72 h** (linter error).

What to do (pick one, never silently):
1. **Split into phases** (preferred): Phase 1 = priority agent + channel + handoff + tests + UAT inside 72 h and 20 days; Phase 2 = the rest as its own SOW or version. Record it in `alcance.fases` and `meta.prioridad`.
2. **Justify** the overrun in `meta.excepcion_horas` (reason, who approved) and/or `meta.excepcion_plazo`; the linter then downgrades the error to a warning.
3. Change `meta.tope_horas` only when the commercial owner agrees a different cap.

The Word shows the Spanish `etiqueta` of every type (field `etiqueta` in `scripts/lib/effort-rates.json`), never the raw key. When the schedule has no slack (20 days) and client dependencies have no date, the effort section states how many of the days depend on them.
